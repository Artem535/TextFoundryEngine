# Standalone `tfe` CLI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the standalone `tfe` executable for TextFoundryEngine with a stable, scriptable command surface, human-readable tables, JSON output, and shell completion for Bash, Zsh, and Fish.

**Architecture:** CLI11 owns argv parsing, subcommands, option validation, and usage errors. A small shared command catalog is the source of truth for parser registration and completion generation. TextFoundryEngine remains the domain/API boundary. Reflect-cpp serializes explicit CLI DTOs; DTO conversion performs validation before calling the engine. FTXUI DOM + Screen render human-readable tables only; JSON output bypasses FTXUI. The first release is a non-interactive CLI; FTXUI Component/TUI is deliberately deferred.

**Tech Stack:** C++23, CMake, vcpkg manifest mode, CLI11 2.x, FTXUI 7.x (`ftxui::dom`, `ftxui::screen`), reflect-cpp, doctest, existing TextFoundryEngine/ObjectBox store APIs.

**Status:** Implemented inline in this worktree, then reworked after an independent review found the initial pass had real defects: `tfe` was missing the ObjectBox `BUILD_RPATH` that `core_tests`/`cli_tests` already carry (the binary could not load `libobjectbox.so`), `vcpkg.json` pinned `ftxui` to a version absent from this project's vcpkg baseline (fixed by bumping the baseline, not the version, to keep FTXUI on vcpkg as decided), `comp create --from-json`'s production conversion path diverged from the one the DTO tests actually exercised (unified onto a single path), `block publish` silently ignored `--version` and forced a full template re-type (replaced with a real `--bump {major,minor}` flag and inherit-unset-fields-from-the-published-block behavior), and dynamic shell-completion (`__complete`) had filesystem side effects on every keystroke and was reverted to the static, catalog-driven completion this plan originally scoped for the first release. Fresh verification passes with `tfe`, `cli_tests` (22 cases, 113 assertions), `core_tests`, and `tfe_smoke`; the ObjectBox-disabled configuration also builds the core and skips `tfe` as designed.

## Global Constraints

- Preserve the existing `build-rel/` untracked directory and unrelated worktree changes.
- Add CLI11 and FTXUI as vcpkg dependencies; do not use FetchContent for the CLI.
- `TEXTFOUNDRY_ENGINE_BUILD_CLI` defaults to `ON`, but the `tfe` target is created only when the ObjectBox store target is available. A clear CMake status message explains the skip when the store is disabled.
- Keep engine/domain types independent of CLI11 and FTXUI.
- Every command supports `--json`; JSON is a single machine-readable document on stdout, while human errors go to stderr.
- Exit status is `0` for success, `1` for an engine/domain failure, and `2` for CLI usage/parsing failure.
- Do not add `replxx`, `tabulate`, an interactive TUI, AI commands, or a generic reflection-driven table renderer in this iteration.
- Do not claim shell completion is provided by CLI11: it is generated by TextFoundryEngine’s own command catalog.
- Use the existing `tf::Result<T>` and `tf::ErrorCode`; do not introduce a second error taxonomy.
